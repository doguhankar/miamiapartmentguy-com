Query 2: List All Policies
  SELECT 
    schemaname, 
    tablename, 
    policyname,
    permissive,
    cmd
  FROM pg_policies 
  WHERE schemaname = 'public' 
  AND tablename IN ('leads', 'saved_lists')
  ORDER BY tablename, policyname;

   - Uses: createAdminClient()
   - Effect: Can INSERT leads regardless of RLS policies
   - Hardcoded: agent_id = 'doguhankar1@gmail.com'
   - RLS Status: BYPASSED (intentional, service role)

2. /api/admin/bulk-upload (POST)
   - Uses: createAdminClient()
   - Effect: Can bulk INSERT leads regardless of RLS policies
   - Hardcoded: agent_id = 'doguhankar1@gmail.com'
   - RLS Status: BYPASSED (intentional, service role)

3. /api/migrate (GET)
   - Uses: createAdminClient() (service role check only)
   - Effect: Can read schema regardless of RLS policies
   - RLS Status: BYPASSED (intentional, service role)

4. /api/lists (POST)
   - Uses: createAdminClient()
   - Effect: Can INSERT saved_lists regardless of RLS policies
   - RLS Status: BYPASSED (intentional, service role)

5. /api/lists/[slug] (GET)
   - Uses: createAdminClient() OR anon client for SELECT
   - Effect: SELECT uses RLS (anon client + public policy)
   - RLS Status: ENFORCED (intentional, public read)

All routes using SUPABASE_SERVICE_ROLE_KEY are server-side only and never
expose the key to client-side code. This is secure by design.

WHAT HAPPENS WHEN AGENTS QUERY LEADS
================================================================================

SCENARIO 1: Agent Don logs in and queries leads

   Query: SELECT * FROM leads ORDER BY created_at DESC
   
   With RLS Applied:
   - Supabase intercepts
   - Extracts: auth.jwt() ->> 'email' = 'doguhankar1@gmail.com'
   - Adds condition: WHERE agent_id = 'doguhankar1@gmail.com'
   - Effective query:
     SELECT * FROM leads 
     WHERE agent_id = 'doguhankar1@gmail.com'
     ORDER BY created_at DESC
   
   Result: Don sees only his leads ✅

SCENARIO 2: Non-authenticated user tries to read leads

   Query: SELECT * FROM leads
   
   With RLS Applied:
   - Supabase intercepts
   - Checks: auth.role() = 'authenticated'? NO (user is anon)
   - Policy condition fails
   - RLS denies: "Permission denied for relation leads"
   
   Result: Query blocked ✅

SCENARIO 3: Form submission inserts lead with service role

   Query: INSERT INTO leads (...) VALUES (...)
   
   With RLS Applied:
   - Supabase sees: auth.role() = 'service_role' (not 'authenticated')
   - Policy conditions checked: auth.role() = 'authenticated'? NO
   - RLS policies DO NOT APPLY to service_role
   - INSERT succeeds
   
   Result: Form submissions work unchanged ✅

SCENARIO 4: Agent tries to edit another agent's lead (multi-agent future)

   Query: UPDATE leads SET name = 'hacked' WHERE id = 42
   
   With RLS Applied:
   - Supabase intercepts
   - Extracts agent email: 'don@example.com'
   - Adds condition: WHERE id = 42 AND agent_id = 'don@example.com'
   - Queries database: Any row matching?
   - Scenario A: Lead 42 owned by Don → Matches → UPDATE succeeds
   - Scenario B: Lead 42 owned by Jane → Doesn't match → UPDATE fails (0 rows)
   
   Result: Multi-tenant isolation automatic ✅
